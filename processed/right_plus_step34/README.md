# right+ 第三、四步：如何使用已经处理好的数据

当前 106 段已全部按“用户确认成功、整段有效、无需裁剪”处理。
本阶段已完成关节定义和跨传感器时间对齐，未启动模型训练。

## 第三步结果：固定观测和动作

- 图像：原始头部 RGB 视频，1280×720、15 FPS；训练时才根据帧索引解码并统一预处理。
- state：右臂 7 个位置反馈＋右手 6 个位置反馈，float32，形状 `[T,13]`。
- action：同样关节顺序的绝对目标位置命令，float32，形状 `[T,13]`。
- 手臂位置单位 rad；手指保留 SDK 抽象值（标称 0～2000），不是弧度。
- 按关节名称匹配，没有按数组位置猜右侧，也没有把六个手指平均成一个值。
- 不以反馈代替动作标签，也不把动作变成未定义的增量。
- 尚未拟合归一化器：下一步按整段示教划分集合后，只用训练集计算。

固定顺序见 joint_schema.json：

每段原始消息中的完整关节名及数值范围也保存在对应的 episodes/*.json；
joint_ranges.csv 汇总全数据的反馈范围和命令范围。
手指反馈最高 2015，略超 SDK 标称 2000；SDK 说明零位可能漂移，因此这里保留原值，不盲目截断。
统计范围不是机器人安全限位。

实录手指 command effort 在 106 段中均固定为 `[13000,8000,8000,8000,8000,8000]`。
已作为 `hand_command_effort` 辅助数组保留，不增加 13 维位置动作的输出维度。
它与文档标称 0～5700 不一致，实际控制适配时需要核对固件及单位，不能按文档想当然截断或直接下发。

## 第四步结果：10 Hz 时间对齐

当前共有 40,097 个规则时间点，其中 40,076 个新鲜度合格，
21 个带新鲜度标记。106 段全部保留。

使用同一 ORIN 的接收时间：关节用 bag timestamp，相机用 CSV 中 receive_unix_ns。
每 0.1 秒，从各路数据中取截至该决策时刻已收到的最新一条；这是后续在线程序可以复现的规则。
拍摄时间和消息 header 时间另行保存，用于延迟诊断，没有统一减去一个假定延迟。

一个实际例子：第一段中某一行的相对决策时间为 10.0 秒，
对应原始视频第 148 帧；该行同时保存 13 维 state 和 13 维 action。
播放器位置约为 9.867 秒，因视频开始时间和接收延迟不同，
它不一定等于相对决策时间。

没有按动作阶段裁剪任务，右臂归位仍属于完整任务。仅在所有数据流共同有记录的时间内建立采样网格。
部分视频开头早于关节记录，最长约 1.047 秒；不填入不存在的测量、不使用未来反馈补开头。
尾部超过共同网格的部分最长约 0.173 秒。源 MP4 和 bag 均完整保留。

接收时刻距离网格时刻超过阈值的点被标记为 valid_sample=False：关节阈值 50 ms，相机阈值 200 ms。
这些行仍在原时间位置；后续训练序列不能跨过它们，不能删行再把两边拼成连续动作。
短暂接收间隔标记和任务是否成功是不同信息。

全量检查分类：
- 拍摄时间相邻帧间隔超过 200 ms：4 段。
- 出现重复拍摄时间戳：1 段（保留帧号与接收时间）。
- 含新鲜度标记的采样点：11 段，共 21 点。
- 手指反馈略超标称范围：84 段，已保留漂移值。
- 视频启动时缺少共同关节覆盖超过 0.25 秒：29 段。

## 以后如何重新运行

已运行完成，无需你重复执行。如果将来需要重做，在现有 robocasa_dp 环境运行：

```bash
cd /home/fx/A2
/home/fx/miniconda3/envs/robocasa_dp/bin/python scripts/a2_prepare_right.py \
  --root data/right/right+ --out processed/right_plus_step34_rerun --hz 10
```

输出目录必须为空，程序会拒绝覆盖已有结果。脚本依赖 numpy、OpenCV，不依赖 ROS 或 GPU。
